# 参考代码中的静态信息采集能力增强清单-v1

## 摘要

本清单用于明确：当前工作目录中的参考代码，哪些静态信息采集与展示能力值得吸收进静态潜客池，哪些明确不吸收。

本轮结论：

- 吸收 `静态背景字段组织`
- 吸收 `公司快照结构`
- 吸收 `主体归一与幂等 enrichment 原则`
- 吸收 `证据展示结构`
- 不吸收探迹依赖流程、联系人体系、动态机会字段和 UI 交互实现

## 二、明确不吸收的能力

### 不吸收内容

1. 探迹依赖流程
2. 浏览器插件执行链路
3. 联系人体系
4. 动态机会字段
5. UI 交互实现
6. `BI切入机会` 作为静态主判断字段

### 原因

- 与外部平台绑定过重
- 容易混淆静态层与动态层
- 容易把当前静态池体系做重

## 三、落地建议

### 进入事实源的内容

只建议进入“静态背景补充字段层”，不进入主判断层：

- 公司产品与服务概述
- 商业模式概述
- 核心客户客群
- 收入规模区间
- 利润状态概述
- 营收增长概述
- 已上线系统概况
- 数字化项目动态
- 相似客户线索
- 主要竞品概述
- 招聘代表岗位
- 近一年重大事件

### 不进入主判断层的内容

- 动态机会信号
- 联系人信息
- 成交概率类判断
- 组织触达优先顺序

## 四、当前结论

参考代码更强的地方，不在潜客判断逻辑本身，而在：

- 静态公司背景信息的结构化组织
- 公司详情卡片的展示结构
- 证据块的展示模型
- 主体归一和 enrichment 的工程约束

静态潜客池下一阶段应优先吸收这些部分。

## 五、额外启发：信息收集路径比字段本身更重要

本轮重新深看参考代码后，额外明确了一点：

- 参考代码真正强的，不只是字段比较全
- 而是它隐含了一条更成熟的收集顺序：
  - 先主体校准
  - 再收基础静态背景
  - 再补系统/招聘/重大事件
  - 最后才生成解释、推荐切口和展示层

### 对静态潜客池的启发

应固定以下收集顺序：

1. `先定主体`
2. `先查官方源`
3. `再补高可信公开源`
4. `再补平台信号`
5. `最后做画像与知识映射`

### 对应参考代码启发点

- `legacy_app/apps/worker/tasks/parse.py`
  - 启发：所有新增信息先归 canonical company
- `deliveries/exporter.py`
  - 启发：把背景字段先组织成稳定快照，再用于导出与交付
- `legacy_app/apps/api/static/app.js`
  - 启发：详情页并不是先做话术，而是先把财务、系统、招聘、事件这类静态背景组织好，再派生切口和展示

### 结论

静态潜客池下一阶段不应只是“继续补字段”，而应把 `收集路径与方法` 固定下来。
