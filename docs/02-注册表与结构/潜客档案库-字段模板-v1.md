# `潜客档案库` 字段模板 v1

## 1. 文档目的

本文件定义 `潜客档案库.xlsx` 的结构、字段和使用边界。

潜客档案层用于承接：

- 每家公司当前已经收集到的结构化信息
- 长段摘录与字段观察
- 额外补充备注
- 档案覆盖状态

它解决的是“调研很多，但主表只留下摘要”的问题。

## 2. 与现有载体的分工

- `静态潜客主表.xlsx`：结论层、筛选层、分层层
- `潜客档案库.xlsx`：公司级已知信息档案层
- `治理与证据.xlsx`：证据与来源层
- `Obsidian note`：解释与协作层

一句话分工：

- 主表存结论
- 档案存已知信息
- evidence 存依据
- note 存解释

### 使用规则

- 主档案表保留当前最佳摘要与长摘录
- 不复制全文
- 长摘录用于提高可读性，不替代 evidence
- 客户事实字段必须优先来自公司级来源
- 不允许继续写入 persona / track 默认模板句
- md 客户档案页只是阅读投影，不是事实源；任何事实补全必须先回写 `潜客档案库.xlsx`
- 缺少公司级事实时，统一回到：
  - `待补官网/年报/IR口径`
  - `待补更强官方披露`
  - `待补公司级市场参考`
  - `待补公司级资产映射`

### 客户事实字段 vs 解释字段

以下字段属于客户事实字段，必须优先来自公司级来源：

- `公司产品与服务概述`
- `商业模式概述`
- `核心客户客群`
- `已上线系统概况`
- `数字化项目动态`
- `招聘代表岗位`
- `近一年重大事件`
- `主要竞品概述`
- `相似客户线索`
- 五个长摘录字段

以下字段属于解释字段，可以保留抽象判断，但不能伪装成客户事实：

- `admission_reason_summary`
- `current_business_problem`
- `primary_jtbd`
- `secondary_jtbd`
- `secondary_persona_tags`
- `management_persona_tags`
- `ICP匹配概率`
- `静态潜客记录成熟度`

### 主画像、次级画像与相关知识资产

- `persona_tag` 代表该潜客当前主判断所采用的主画像
- `secondary_persona_tags` 代表辅助解释、边界观察或相邻画像，不替代主画像
- `knowledge_asset_refs` 只记录强相关知识资产，用于帮助用户理解“为什么这家公司值得关注、像在哪里、还可参考什么”
- `knowledge_asset_refs` 可以在档案页展示给用户参考，但不能替代公司级事实字段

### 逐客户修复是默认工作流

自 `2026-04-03` 起，客户档案不再按字段做大面积半成品修复，而改成：

1. 逐客户补事实层
2. 逐客户收口解释层
3. 回写结构化层
4. 重建 md 页面
5. 单客户自检通过后再 mark

只有达到“用户可用”的客户档案，才允许把 `archive_repair_status` 标成 `已修复`。

### `信息扎实度` 当前判定口径

- `高`
  - 官方源稳定
  - 高可信源稳定
  - 至少 3 个公司事实字段有公司级内容
  - 至少 2 个长摘录为来源型摘录
  - 至少 1 项公司级市场参考，或已明确沉淀重点公司 note / 公司级资产映射
- `中高`
  - 官方源稳定
  - 至少 2 个公司事实字段有公司级内容
  - 至少 1 个来源型摘录
- `相关资产与状态`
  - 仅在存在公司级资产映射，或已明确沉淀重点公司 note 时展示
  - 默认知识资产/话术引用不再自动作为“公司级资产映射”给 `信息扎实度` 加分
- `市场参考`
  - 仅在存在公司级竞品或相似样本信息时展示
- `中`
  - 主体可识别
  - 但公司事实字段偏薄
- `中低`
  - 主体或来源都薄
  - 公司事实字段几乎全缺

## 7. `profile_coverage`

### 粒度

- 一行一家公司

### 字段

| 字段名 | 中文名 | 说明 |
| --- | --- | --- |
| `account_id` | 账户 ID | 主键 |
| `target_scope` | 目标层级 | 当前一般对应 `L1-L4` |
| `required_field_count` | 要求字段数 | 当前层级应达到的最低字段数 |
| `filled_field_count` | 已填字段数 | 当前已满足字段数 |
| `coverage_ratio` | 覆盖率 | 已填 / 要求 |
| `official_source_ready` | 官方源就绪 | `yes / no` |
| `high_confidence_ready` | 高可信来源就绪 | `yes / no` |
| `profile_complete_status` | 档案完整度状态 | `not_started / minimum_ready / standard_ready / high_quality_ready` |
| `missing_core_fields` | 缺失核心字段 | 分号分隔 |
| `next_action` | 下一步动作 | 应继续补什么 |

### 当前默认标准

- `L1-L2`：`high_quality_ready`
- `L3`：`standard_ready`
- `L4`：`minimum_ready`

### 修复状态字段使用规则

- `archive_repair_status`
  - `未修复`：还没进入逐客户修复批次
  - `修复中`：本批处理中，尚未最终通过
  - `已修复`：已按客户事实优先标准重建，单页自检通过
  - `待复核`：本轮修过，但仍需复核
- `archive_repair_batch`
  - 标记本次所属批次，供索引和批次报告回溯
- `archive_repair_checked_at`
  - 标记最近一次通过或待复核的时间
- `archive_repair_note`
  - 记录修复说明或待复核原因

## 8. 当前实现边界

- 第一批覆盖 `L1-L4`
- 不引入动态机会字段
- 招聘、系统、重大事件仍只按静态背景事实口径使用
- 重点公司 note 仍只覆盖代表样本，不覆盖全部 `L1-L4`
