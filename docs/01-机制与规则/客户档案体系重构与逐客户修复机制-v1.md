# 客户档案体系重构与逐客户修复机制-v1

## 1. 目标

本机制用于统一当前客户档案体系的三件事：

1. 客户档案的事实层、解释层、阅读层边界
2. 客户档案页的固定结构
3. 后续修复与补强的默认工作流

一句话定义：

- `Excel` 是事实层
- `md` 是阅读层
- 解释层保留，但后置、精简、知识库驱动
- 后续不再按字段批量半成品修，而按客户逐个修复

适用边界补充：

- 本文只定义 `客户档案层` 的修复机制
- 不定义整个静态潜客池的总主线
- 不替代“知识库 -> 画像 -> 候选 -> 上移补强”的系统闭环
- 仅当档案层确实服务上移、共享、专题消费或重点对象阅读时，才应触发逐客户修复

## 2. 四层分工

### 结论层
- 载体：`静态潜客主表.xlsx`
- 作用：分层、筛选、轻量摘要

### 档案事实层
- 载体：`潜客档案库.xlsx`
- 作用：公司级已知信息、长摘录、字段观察、缺口状态

### 证据层
- 载体：`治理与证据.xlsx`
- 作用：来源与字段级依据

### 阅读层
- 载体：`L3+` 客户档案页、重点公司 note、专题包
- 作用：阅读、协作、分享

## 3. 核心边界

### 3.1 md 不是事实源

客户档案 md 页固定定义为：

- 结构化事实层的阅读投影
- 不是信息源
- 不是原始材料仓库
- 不是上移判定源

任何事实补全，必须先回写：

- `潜客档案库.xlsx`
- 必要时 `治理与证据.xlsx`

然后再重建 md 页。

### 3.2 事实层与解释层分开

事实层字段：

- `公司产品与服务概述`
- `商业模式概述`
- `核心客户客群`
- `已上线系统概况`
- `数字化项目动态`
- `招聘代表岗位`
- `近一年重大事件`
- `主要竞品概述`
- `相似客户线索`
- 五类长摘录

解释层字段：

- `persona_tag`
- `management_persona_tags`
- `admission_reason_summary`
- `ICP匹配概率`
- `静态潜客记录成熟度`
- `信息扎实度`
- `knowledge_asset_refs`
- `talk_track_refs`

解释层不是人工评语层，而是：

- 知识库对客户的结构化投影

### 3.3 严禁再次发生的错误

以后不允许：

- 用画像模板句写回事实字段
- 用经营诉求反推系统/数字化事实
- 用默认相似样本冒充市场事实
- 因页面空而写入看起来合理的泛化句

### 3.4 档案修复不是全局默认主流程

客户档案修复在当前体系中的正确位置是：

- 阅读层质量增强
- 共享层稳定化
- 上移前后的辅助补强

它不是：

- 知识库建设的替代物
- 画像扩展的替代物
- `L5` 候选扩展的替代物
- 上移判断本身

因此后续默认理解应固定为：

- `档案修复服务主线`
- 不是 `主线服务档案修复`

## 4. 客户档案页固定结构

### 1. 公司是谁
- 公司名称
- 主线
- 当前层级
- 静态优先级
- 业务形态画像

### 2. 公司具体信息
- `2.1` 主营产品与服务
- `2.2` 商业模式
- `2.3` 核心客户/渠道/场景
- `2.4` 档案评估状态
- `2.5` 系统与数字化现状
- `2.6` 近一年重大事件
- `2.7` 招聘/组织信号
- `2.8` 市场参考（条件展示）

条件区块：

- `经营复杂度特征`
  - 只有有公司级事实时才展示

### 3. 关键事实摘录
- 官网/官方资料摘录
- 年报/招股书/IR 摘录
- 已验证案例材料摘录

### 4. 当前缺口
- 缺哪些事实
- 缺哪些来源
- 下一步补什么

### 5. 为什么值得看
- `5.1` 画像匹配
- `5.2` 为什么值得看
- `5.3` 可切入与可复用资产

### 6. 来源概览
- 来源类型
- 来源路径/链接
- 官方源数量
- 高可信源数量
- 最近更新时间

## 5. 信息扎实度口径

`信息扎实度` 必须与页面前半部分实际可读到的公司级事实一致，不能靠：

- 来源就绪
- 默认资产包
- 默认样本参考
- 默认匹配层

来抬高。

当前口径：

- `高`
  - 至少 3 个公司事实字段有公司级内容
  - 至少 2 个来源型摘录
  - 主体清晰
  - 官方源和高可信源稳定
- `中高`
  - 至少 2 个公司事实字段有公司级内容
  - 至少 1 个来源型摘录
  - 主体清晰
  - 官方源稳定
- `中`
  - 主体可识别
  - 但事实字段仍偏薄
- `中低`
  - 事实字段几乎全缺
  - 或来源仍薄

## 6. 档案修复触发后默认工作流

从 `2026-04-03` 起，一旦确定需要做客户档案修复，默认按以下工作流执行：

1. 选定一批客户
2. 按客户逐个补事实层
3. 按客户逐个收口解释层
4. 回写结构化层
5. 统一跑 normalize
6. 统一跑 render
7. 跑 batch quality check
8. 单客户自检通过后再 mark

不再采用：

- 先补某个字段一大片
- 再补另一个字段一大片
- 页面更满了，但单家公司仍不可用

触发场景通常应限于：

- 某一轮上移对象需要定向补强
- 某批重点公司需要进入共享或专题材料
- 某批 `L3+` 页面质量已经明显阻碍阅读与协作

如果只是为了让页面更完整、更饱满，但不直接服务上述目标，不应默认启动大面积逐客户修复。

## 7. 单客户完成标准

一家公司被标成 `已修复` 前，至少必须满足：

- `公司产品与服务概述` 达到公司级事实标准
- `商业模式概述` 达到公司级事实标准
- 来源层能解释页面前半部分事实从哪来
- 解释层已经收口
- 单页自检通过

`核心客户客群` 仍保留在中优先级最后一位：

- 有可靠来源就补
- 没有就留缺口
- 不允许为完整感硬填

## 8. 批次与标记机制

默认采用 `Excel + 索引双标记`。

### Excel
在 `潜客档案库.xlsx / account_profiles` 使用：

- `archive_repair_status`
- `archive_repair_batch`
- `archive_repair_checked_at`
- `archive_repair_note`

状态值固定为：

- `未修复`
- `修复中`
- `已修复`
- `待复核`

### 索引
同步更新：

- `L3以上客户档案索引.md`
- `L3以上客户档案索引-团队共享.xlsx`

### 页面
每个已修复页面顶部增加：

- `档案修复状态：已修复（batch_xx）`

## 9. 批次报告

每一批修完后必须产出批次报告，至少包括：

1. 本批对象清单
2. 每家修了什么
3. 使用了哪些来源
4. 哪些字段仍保留缺口
5. 本批发现的共性问题
6. 本批已完成 mark 的范围

## 10. 本机制内部执行顺序

### 第一阶段
- 统一修架构、规范、页面结构、扎实度逻辑、修复标记机制

### 第二阶段
- 开始逐客户修全部 `L1`
- 不区分分享状态
- 默认每批 `12` 家

### 第三阶段
- 再处理剩余 `L3`

补充说明：

- 以上顺序只描述“档案修复机制内部”在当时的推进顺序
- 不代表当前整个静态潜客池项目的全局默认优先级
- 当前全局默认优先级仍应以知识库、画像、候选扩展和上移补强为先
