# 团队共享层最小化设计 v1

## 1. 目标

未来给团队分享时，不再尝试共享整个 vault，也不再默认共享全量静态池。

最小化团队共享层固定为：

1. `L3+ 客户档案 note`
2. `L3+ 客户档案索引 Excel`
3. 必要时附少量专题包

这样做的目的：

- 降低团队阅读成本
- 降低维护成本
- 避免把治理层、过程层、archive 和个人工作流一起暴露出去
- 让“已分享”和“后续更新”可追踪

## 2. 共享层与内部层分工

### 2.1 团队共享层

默认进入团队包的对象：

1. `L3+ 客户档案页`
2. `L3+ 客户档案索引 Excel`
3. 需要协作时的专题包
4. 少量被明确选中的重点公司 note

### 2.2 内部保留层

继续内部保留，但不作为团队默认交付物：

- `静态潜客主表.xlsx`
- `潜客档案库.xlsx`
- `治理与证据.xlsx`
- `主线与画像注册表.xlsx`
- `知识资产注册表.xlsx`
- 全量浏览视图
- 规则、执行、校验、archive
- 老客排除、queue、evidence 明细

## 3. 分享状态模型

### 3.1 适用对象

需要加分享状态的对象：

1. `L3+ 客户档案页`
2. `L3+ 客户档案索引 Excel` 中的公司记录
3. 若进入团队包的专题包
4. 若进入团队包的重点公司 note

### 3.2 状态值

统一使用：

- `未分享`
- `已分享`
- `已更新`

含义如下：

#### `未分享`

- 尚未进入任何团队共享包

#### `已分享`

- 已进入某次团队共享包
- admin 已确认
- 默认后续不再修改共享内容

#### `已更新`

- 该对象过去已经分享过
- 后续内容又发生了变更
- 下一次打包时应明确标记为“更新”，而不是“新增”

## 4. admin 确认机制

团队共享流程固定为：

1. 先生成本次团队包候选清单
2. 由 admin 确认哪些对象进入本次共享
3. 被确认对象标记为 `已分享`
4. 后续默认冻结，不主动修改
5. 如果确实修改，则改标为 `已更新`

## 5. 打包输出规则

每次团队包都只区分两类内容：

1. `新增档案`
2. `已更新档案`

### `新增档案`

- 以前从未分享过
- 本次第一次进入团队包

### `已更新档案`

- 以前已经分享过
- 本次有内容变化
- 打包时必须明确标注“非新档案，为更新版”

## 6. 团队包建议结构

### 6.1 必选内容

1. `L3+ 客户档案索引 Excel`
2. `新增档案`
3. `已更新档案`

### 6.2 可选内容

按场景附加：

- 零售消费专题包
- 跨境电商专题包
- 先进制造专题包
- 少量重点公司解释页

## 7. 对现有文件的影响

### 7.1 继续保留，但降级为内部层

以下文件继续保留，但不再作为团队默认交付物：

- `内部运营-静态潜客池-共享版.xlsx`
- 全量浏览视图
- 全量汇总页
- 大部分状态页

这些内容仍然有价值，但主要服务：

- 内部运营
- 清洗
- 上移
- 事实核验

而不是服务团队最小共享。

### 7.2 当前团队默认交付主轴

未来团队共享主轴应转为：

1. `L3+ 客户档案页`
2. `L3+ 客户档案索引 Excel`
3. `专题包（按需）`

## 8. 与 skill 的关系

`static-pool-share` 后续默认应优先产出：

1. `L3+ 客户档案索引 Excel`
2. `新增档案清单`
3. `已更新档案清单`
4. 必要时附专题包

而不是默认导出整个共享版工作簿或整个 vault。

## 9. 默认结论

一句话收口：

未来团队共享不再追求“共享整个系统”，而是只共享“当前足够成熟且值得协作消费的内容”。

因此默认策略就是：

- `L3+` 才进入团队共享主层
- admin 确认后标记为 `已分享`
- 后续默认不改
- 如果改了，标记为 `已更新`
- 打包时明确区分 `新增` 和 `更新`
