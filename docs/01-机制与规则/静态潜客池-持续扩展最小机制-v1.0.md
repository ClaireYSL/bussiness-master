# 静态潜客池持续扩展最小机制 v1.0

## 1. 文档目的

本文件定义 `Milestone 2` 的最小版持续扩展机制。

目标不是设计完整运营系统，而是保证：

1. 静态潜客池可以继续增长
2. 新增不会继续污染事实源
3. 主表、证据、去重机制保持稳定

## 2. 机制范围

本机制固定只做两件事：

1. `扩池`
2. `事实源维护`

以下动作不做固定节奏：

- 上移
- 复盘

它们仅在用户明确要求时触发。

## 3. 新增入池最小路径

任何新账户进入 `L5` 前，必须按以下顺序检查：

1. 查 `account_alias_registry_v1`
2. 查清洗后主表中是否已存在 canonical_name
3. 做老客排除
4. 明确主线
5. 明确主画像
6. 写一句话入池理由
7. 补最小证据
8. 标记待验证项
9. 才允许进入 `L5`

## 4. 新账户入 L5 的最低字段要求

任何新账户进入 `L5` 时，必须至少具备：

- `account_id`
- `account_canonical_name`
- `primary_track`
- `persona_tag`
- `pool_layer=L5`
- `static_priority`
- `admission_reason_summary`
- `source_note`
- `validation_gap`

## 5. 最小证据约束

新账户入 `L5` 时，必须至少有：

1. 1 条最小证据
2. 证据类型明确
3. 证据来源明确
4. 能支撑：
   - 主线
   - 画像
   - 入池理由

## 6. queue 最小使用方式

在 `Milestone 2` 中，queue 只保留最必要的三类用途：

- `verification`
- `cleanup_review`
- `promotion_review`

说明：

- `promotion_review` 只在用户明确要求上移时使用
- 不再引入复杂运营队列类型

## 7. 知识资产使用原则

知识资产继续保留，但只按需补，不单独运营化。

触发补充的场景：

1. 某类画像解释不足
2. 某类账户判断卡住
3. 用户要求解释原因
4. 用户要求新增画像 / 新行业

## 8. Milestone 2 不做的事情

明确不纳入：

- 固定周节奏的上移机制
- 固定月节奏的复盘机制
- 动态机会层
- 联系人层
- CRM 集成
- 复杂运营系统设计

## 9. 当前执行默认值

当前默认值锁定为：

- 新增时先查 alias
- 新增时先查清洗后主表
- `万得福 / 建发` 继续视为边界主体
- 上移按用户要求触发
- 复盘按用户要求触发
