# 静态潜客信息收集路径与方法设计-v1

## 摘要

本方案回答两个问题：

1. 静态潜客池应从哪里收集信息
2. 应按什么顺序、用什么方法收集，才能尽快把 `信息扎实度` 提升到较高水平

本方案基于当前已确认边界：

- 当前只服务 `静态潜客池`
- 不引入动态机会层
- 不引入联系人体系
- 不接探迹依赖流程
- 不复用 UI 交互实现
- Excel 仍是唯一事实源
- 画像、知识资产、话术资产仍由人工/LLM判断与解释层承载

本轮重点不是增加更多判断字段，而是固定一条更稳的信息收集路径：

1. `先定主体`
2. `先收官方源`
3. `再补高可信公开源`
4. `再补平台信号源`
5. `最后做画像与知识映射`

边界约束参见：

- `/Users/clairaipartner/Codex/bussiness-master/docs/01-机制与规则/静态潜客信息与动态机会信息边界说明-v1.md`

## 一、目标

### 1. 提升信息扎实度

让静态潜客池中的公司，不再只有“像不像 ICP”的抽象判断，而是有一套足够厚的静态背景支撑。

### 2. 降低误判率

避免以下常见问题：

- 品牌名和法人主体混淆
- 先入池后发现主体不对
- 先有画像判断，后倒推找信息
- 相同主体被反复 enrich 后出现多版本背景快照

### 3. 提高收集效率

通过固定来源优先级和收集顺序，减少“每次都从头判断去哪里找”的重复成本。

---

## 二、设计原则

### 原则 1：事实采集在前，解释判断在后

先收公司静态事实，再做：

- `ICP匹配概率`
- 管理诉求画像判断
- 知识资产映射
- 切入话术选择

### 原则 2：主体归一优先于一切字段采集

所有新信息必须先挂到 canonical account，再进入：

- 主表
- evidence
- 重点公司 note
- 共享版
- 专题包

### 原则 3：官方源优先，高可信源补充，平台信号辅助

来源优先级必须固定，避免把弱信号当作主事实。

### 原则 4：字段分层，不把所有采集结果都塞进主判断区

静态背景字段用于增强 `信息扎实度` 和解释层，不直接取代三大判断字段。

## 四、收集路径优先级

## Layer 1：主体归一层

### 目标

确定这家公司到底是谁，避免后续所有信息挂错主体。

### 主要动作

1. 查 `alias_registry`
2. 查当前事实主表
3. 识别：
   - 品牌名
   - 集团名
   - 法人主体
   - 历史别名
4. 落到唯一 canonical account

### 参考代码启发

- `legacy_app/apps/worker/tasks/parse.py` 的 `resolve_company`
- 重点不是代码本身，而是“所有信号先归 canonical company”的原则

### 输出

- `account_id`
- `account_canonical_name`
- alias 是否已存在
- 是否疑似重复主体

---

## Layer 2：官方源收集层

### 目标

尽快拿到最可信的静态背景信息。

### 主要来源

1. 企业官网
2. 年报 / 财报 / 招股书
3. 投资者关系页面
4. 官方新闻中心 / 官方公众号
5. 官方招聘页

### 适合收集的字段

- 公司产品与服务概述
- 商业模式概述
- 核心客户客群
- 收入规模区间
- 营收增长概述
- 已上线系统概况（若公开披露）
- 数字化项目动态（若公开披露）
- 近一年重大事件

### 使用规则

- 官方源优先作为主事实来源
- 若官方源没有，再进入下一层

### 参考代码启发

- `deliveries/exporter.py` 中对官网、收入、增长、系统、重大事件的统一导出字段组织
- `app.js` 中把“官网 / 财务 / 系统 / 重大动态”作为详情主体骨架

---

## Layer 3：高可信公开源补充层

### 目标

在官方源不足时，补充高可信公开信息。

### 主要来源

1. 交易所公告
2. 权威媒体专访
3. 行业研究或协会公开资料
4. 政府 / 展会 / 项目公开页面

### 适合收集的字段

- 营收增长概述
- 利润状态概述
- 重大事件
- 数字化项目动态
- 相似客户线索
- 主要竞品概述

### 使用规则

- 可作为背景补充
- 若与官方源冲突，以官方源优先
- 必须记录来源和时间

---

## Layer 4：平台信号补充层

### 目标

补足那些不一定在官方材料里直接出现、但能反映经营复杂度和数字化状态的公开信号。

### 主要来源

1. 招聘平台
2. 电商平台 / 独立站 / 渠道页面
3. 产品目录 / 展会页面
4. 企业公开资料平台

### 适合收集的字段

- 招聘代表岗位
- 数字化项目动态
- 已上线系统概况
- 产品与服务结构
- 商业模式线索
- 核心客户客群线索

### 使用规则

- 这是辅助层，不应单独作为主判断锚点
- 适合作为：
  - “经营复杂度提示”
  - “系统/数字化痕迹提示”
  - “当前组织关注点提示”

### 参考代码启发

- `app.js` 中招聘和系统信号被用作“推荐切口”与“为什么现在值得看”的组成部分
- 这对静态层的意义不是动态机会判断，而是静态背景增厚

---

## Layer 5：内部映射与解释层

### 目标

在静态事实采集完成后，才进入解释层判断。

### 主要来源

1. 画像注册表
2. 知识资产注册表
3. 重点公司 note
4. 既有样本客户
5. 切入话术资产

### 适合产出的内容

- 业务形态画像判断
- 管理诉求画像判断
- ICP匹配概率校准
- 切入话术建议
- 专题包组织

### 使用规则

- 这是解释层，不替代事实采集
- 不应反向把解释资产当成背景事实

---

## 五、收集顺序设计

## 推荐顺序

1. `先定主体`
2. `先查官方源`
3. `再补高可信公开源`
4. `再补平台信号`
5. `最后做画像与知识映射`

## 不推荐顺序

1. 先觉得它像 ICP
2. 再倒推找支持证据

### 原因

这种顺序容易：

- 放大确认偏误
- 让弱证据看起来像强判断
- 让 `ICP匹配概率` 与 `信息扎实度` 混在一起

## 七、哪些部分需要代码保障

## 应优先代码化

1. canonical / alias 检查
2. 官网与基础主体快照采集
3. 招聘信号采集
4. 重大事件采集
5. 公开系统/数字化痕迹采集
6. 证据来源与时间记录

## 暂不代码化

1. `ICP匹配概率`
2. 管理诉求画像判断
3. 重点公司解释
4. 知识资产映射
5. 切入话术选择

### 原因

这些内容当前更适合：

- 人工判断
- LLM 辅助
- 模板约束

而不是过早做成固定程序逻辑。

## 八、对现有 4 个 skill 的影响

## `static-pool-expand`

必须显式采用以下执行顺序：

1. canonical / alias 检查
2. 官方源最小事实采集
3. 高可信源补充
4. 平台信号补充
5. 最小证据写入
6. 入池
7. 管理诉求画像建议
8. 必要时新建重点公司 note

## `static-pool-cleanup`

必须新增：

- 背景字段冲突清理
- enrichment 幂等复核
- 同主体多版本背景快照校对

## `static-pool-promote`

必须明确：

- 上移前优先补官方源和高可信源
- 不以平台信号单独支撑成熟度上移

## `static-pool-share`

必须明确：

- 分享层优先消费背景快照字段
- 不直接暴露采集过程细节
- 对仍待验证内容保留标记

---

## 九、验收标准

当以下条件满足时，说明这套收集路径设计有效：

1. 新增公司时，先定主体再补背景字段
2. 重点公司的背景快照能回到官方源或高可信源
3. 平台信号只作为辅助，不会冒充主判断依据
4. `信息扎实度` 的提升能够对应到更厚的背景与证据
5. 4 个 skill 的执行路径与这套方法保持一致

---

## 十、结论

为了尽快把静态潜客池的信息可靠度拉高，最重要的不是继续增加更多抽象判断字段，而是固定：

1. `从哪里收`
2. `按什么顺序收`
3. `哪些用代码保障`
4. `哪些继续由人工/LLM判断`

当前最优路径是：

- `主体归一`
- `官方源优先`
- `高可信公开源补充`
- `平台信号辅助`
- `解释层后置`

这条路径比“先觉得像、再找支持信息”更稳，也更能持续提高 `信息扎实度`。

同时必须配合以下边界：

- 背景事实进入静态层
- 时机判断后置到动态层

否则即使收集路径正确，也会在使用阶段把静态池重新污染成“机会池”。
