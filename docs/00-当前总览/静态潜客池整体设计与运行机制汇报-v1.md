## 2. 为什么要建静态潜客池

我们最初要解决的问题，不是“找一批公司名”，而是要建立一个长期有效的外部目标客户池基础设施。

如果没有这层基础设施，团队会长期遇到这些问题：

1. 同一家公司反复被不同人重复判断
2. 名单很多，但标准不一致
3. 结论很多，但证据很薄
4. 案例和经验无法沉淀成可复用资产
5. 潜客判断和动态机会判断容易混在一起

所以我们把潜客池拆成了两层：

- `静态潜客池`
- `未来动态机会池`

其中静态池先解决：

- 谁应该长期在池里
- 我们为什么判断它像目标客户
- 我们已经知道了这家公司哪些关键信息

动态池以后再解决：

- 谁现在更值得优先动作
- 是否有时间敏感机会窗口

## 3. 当前整体架构

当前静态潜客池已经形成了清晰的四层结构。

### 3.1 知识层

唯一事实源是 Excel。

核心工作簿包括：

- `静态潜客主表.xlsx`
- `潜客档案库.xlsx`
- `治理与证据.xlsx`
- `主线与画像注册表.xlsx`
- `知识资产注册表.xlsx`

这里的分工是：

- `知识资产注册表`：存原始素材盘点、学习队列、正式知识资产
- `主线与画像注册表`：存主线、业务形态画像、管理诉求画像定义

知识层回答的是：

- 我们已经学到了什么
- 这些知识支撑哪些主线与画像
- 哪些真实素材还需要继续学习

### 3.2 判断与候选层

`静态潜客主表`、`治理与证据`、`review queue` 共同承载这一层。

这一层回答的是：

- 这家公司属于哪条主线
- 更像哪个画像
- 是否满足 `L5` 最低入池标准
- 本轮是否接近上移
- 补完信息后是否应该升层

这里真正驱动系统增长的是：

- `知识 -> 画像 -> L5 候选 -> 上移`

而不是：

- `先把全部档案修厚，再决定谁值得判断`

### 3.3 档案与阅读层

这是支撑层，不是主驱动层。

`潜客档案库` 与 Obsidian 阅读层共同承载：

- `潜客档案库.xlsx`
- `L3+` 客户档案页
- 重点公司 note
- 总览页、浏览页、专题包

它的作用是：

- 展开展示每家公司已经知道了什么
- 记录哪些字段还没补
- 承载长摘录和补充备注
- 让共享、阅读、专题消费更顺畅

需要特别强调：

- 档案层很重要
- 但档案层不替代知识库建设
- 不替代画像扩展
- 不替代候选发现
- 也不替代上移判断本身

### 3.4 制度与执行层

repo `docs/` 承担：

- 规则
- 结构定义
- 执行记录
- 里程碑状态
- 历史归档

所以现在职责应理解为：

- `知识资产注册表 / 主线画像注册表 = 知识与定义层`
- `主表 / evidence / queue = 判断与候选层`
- `档案库 / Obsidian = 阅读与共享层`
- `repo docs = 制度、执行与归档层`

## 4. 当前静态潜客池的核心判断模型

当前已经明确不再用一个模糊层级同时承载所有判断，而是采用三字段并行：

1. `信息扎实度`
2. `ICP匹配概率`
3. `静态潜客记录成熟度`

### 4.1 信息扎实度

回答：

- 我们对这家公司当前掌握的信息有多完整、多可靠

它强调的是：

- 来源质量
- 证据是否充分
- 关键事实是否已补齐

### 4.2 ICP匹配概率

回答：

- 基于当前已知信息，我们判断这家公司符合目标客群画像的概率有多高

它不是客观真值，而是阶段性判断。

### 4.3 静态潜客记录成熟度

回答：

- 这条记录在静态池中的综合成熟度处于哪一层

对应 `L1-L5`：

- `L1`：高成熟、低缺口、可长期稳定保留的成熟潜客层
- `L2`：高成熟、高可信但仍有一定缺口的成熟潜客层
- `L3`：可读、可治理、可继续补强的潜客层
- `L4`：较成熟候选层
- `L5`：最低入池候选层

它不是：

- 成交概率
- 当前机会强弱
- 销售优先级
- 重点公司标签
- 高质量客户样本标签

需要单独区分：

- `L1 / L2 / L3` 回答的是：这条潜客记录有多成熟、多稳
- `重点公司 / 高质量客户样本` 回答的是：这家公司值不值得被反复拿来解释、分享和复用

### 4.4 静态优先级

静态优先级作为层内排序使用，当前用 `A/B/C` 表示。

它的含义是：

- 在同一层内，谁更值得优先补证、优先解释、优先上移

不是动态机会优先级。

## 5. 当前画像体系

当前画像体系已经从单一业务画像，扩展成两层并行：

1. `业务形态画像`
2. `经营诉求画像`

### 5.1 业务形态画像

业务形态画像回答：

- 这家公司在经营结构上属于哪一类

当前 active 业务形态画像 `7` 个，覆盖三条主线：

- 零售消费
- 跨境电商
- 先进制造

典型画像包括：

- 多门店连锁零售
- 高 SKU 品牌消费品
- 连锁餐饮 / 茶饮 / 咖啡
- 多平台品牌出海型
- 供应链复杂的跨境经营型企业
- 多工厂离散制造集团
- 研产销协同复杂的技术型制造企业

### 5.2 经营诉求画像

经营诉求画像回答：

- 这类公司更可能因为什么管理问题被打动

当前 active 经营诉求画像 `5` 个：

- 总部经营穿透诉求型
- 利润改善诉求型
- 库存与供应链协同诉求型
- 一线动作闭环诉求型
- 集团协同与经营驾驶舱诉求型

这样以后我们看一家公司，不只知道它“是什么业务形态”，还知道它“更像哪类经营问题对象”。

## 6. 当前知识库体系

知识层已经不只是案例堆积，而是可复用资产体系。

当前知识资产主要分为：

1. 行业洞察
2. 客户案例
3. 方案打法
4. 映射资产
5. 切入话术

知识资产的作用是：

- 支撑为什么这家公司值得进入静态池
- 支撑为什么它适合归到某个画像
- 支撑以后怎么讲、怎么解释、怎么分享
- 支撑后续继续扩 `L5` 候选
- 支撑上移时的强核验与重判

知识资产已经和：

- 主线
- 画像
- 重点公司
- `L3+` 客户档案
- 专题包

形成了稳定挂接关系。

一句话说：

- 不是“先有公司，再临时解释”
- 而是“先有知识，再更稳定地解释和找公司”

## 7. 正确的运行顺序

为了避免后续执行再次偏离，当前默认顺序应固定为：

1. `原始素材持续学习`
2. `知识库增强`
3. `主线 / 画像增强`
4. `基于画像扩展 L5 候选`
5. `在上移过程中补证、补事实、重判三大判断字段`
6. `按需修复档案与阅读层`

这意味着：

- 先扩知识，再扩画像，再扩池
- 档案修复只在明确服务上移、共享、专题消费时进入前台
- 不再把“逐客户修档案”当作默认主任务

---

## 8. 客户档案修复的正确位置

`客户档案逐客户修复` 是当前体系中的支持性动作，主要服务：

- `L3+` 阅读可用性
- 共享材料稳定性
- 专题包消费
- 上移时减少重复查找成本

它不应反向成为：

- 当前仓库的第一优先级总任务
- 潜客池主线本身
- 知识库和画像工作的替代物

正确关系应是：

- `档案修复服务主线`
- 不是 `主线服务档案修复`

我们现在不是只知道“哪个公司像”，而是开始知道“为什么像、拿什么解释、从什么问题切”。

## 7. 当前静态潜客池如何持续工作

当前静态池已经不是一次性名单，而是一个持续运行机制。

### 7.1 扩池

通过 `static-pool-expand` 处理新候选。

当前规则已经明确：

- 候选来源可以很多，但要优先来自：
  - 高质量样本外扩
  - 历史候选池清洗
  - 画像驱动补池
  - 官方源 / 高可信公开源行业扫描
- 用户给的一批名单，只是“候选来源”，不是“可直接入池结果”

写入 `L5` 前，必须先做：

1. alias 检查
2. 老客排除
3. 主体归一
4. 静态合理性初筛
5. 最小证据补齐
6. 最小背景字段补齐

### 7.2 清洗

通过 `static-pool-cleanup` 处理：

- 重复主体
- alias
- canonical 归一
- 历史脏数据
- 背景字段冲突

### 7.3 上移

通过 `static-pool-promote` 处理上移。

当前上移的定义已经很清楚：

- 不只是改层级字段
- 而是完成：
  - 补强证据
  - 重判三大字段
  - 升层
  - 同步主表、档案、evidence、queue、档案页

并且规则已经明确：

- 当账户第一次进入 `L3+` 时，自动生成客户档案页
- 后续继续从 `L3 -> L2` 或 `L2 -> L1`，更新原档案页
- 不重复建第二份

### 7.4 分享

通过 `static-pool-share` 处理分享。

当前我们已经把分享层简化成：

- `L3+ 客户档案页`
- `L3+ 客户档案索引 Excel`

而不是把整个 vault 原样发给团队。

## 9. 当前系统的主要优势

我认为当前这套静态潜客池，主要有以下优势。

### 9.1 边界清楚

这是最大优势。

静态池和未来动态机会层没有混掉。

所以我们现在清楚知道：

- 静态池回答“谁应该长期在池里”
- 动态池以后回答“谁现在更值得先动”

### 9.2 分层清楚

现在已经形成清楚的信息分层：

- 主表存结论
- 档案库存已知信息
- evidence 存依据
- note 存解释

这比“一张大表解决一切”稳定得多。

### 9.3 机制可持续

我们已经不需要每次从零决定怎么扩池、怎么上移、怎么分享。

已经有：

- expand
- cleanup
- promote
- share

四个稳定入口。

### 9.4 解释能力强

很多系统只能告诉你“公司在名单里”，但解释不清为什么。

而我们现在已经可以解释：

- 它属于什么业务形态画像
- 它更像哪类经营问题对象
- 已经知道了哪些关键信息
- 还能拿什么案例、方案、话术去讲

### 9.5 适合逐步升级

当前系统不重、不依赖复杂系统，但已经给未来升级预留了足够接口。

这意味着：

- 现在能跑
- 后面还能继续做厚

## 11. 后续如何继续运作

接下来不建议再回到“重新设计大框架”，而应该按现有机制持续推进。

### 11.1 对静态池本身

下一步重点应该是：

1. 继续补强新进入 `L3` 的官方源和高可信源证据
2. 从新 `L3` 里再筛一批对象做 `L3 -> L2`
3. 继续厚化高质量样本的档案和重点公司解释层

### 11.2 对团队协作

等高质量档案再厚一些后，团队分享可以按最小机制启动：

- 定期导出：
  - `L3+ 客户档案页`
  - `L3+ 客户档案索引 Excel`
- admin 确认后标记：
  - `已分享`
- 后续如果有改动，再标：
  - `已更新`

这样团队看到的是：

- 新增档案
- 更新档案

不会被全量内部材料干扰。

## 12. 未来如何与动态机会池协作

未来动态机会池不应该推翻静态池，而应该建立在静态池之上。

我建议后续的协作关系是：

### 静态池负责

- 谁应该长期在池里
- 这家公司像不像 ICP
- 我们对它已经知道了什么
- 哪些公司是高质量样本

### 动态池负责

- 这家公司现在是否出现时间敏感窗口
- 是否值得优先跟进
- 当前是否有组织变化、预算、项目、互动信号

### 两层协作方式

未来真正的优先顺序，不应该只看其中一层，而应该叠加：

- 静态匹配和成熟度
- 动态机会强弱

一句话说：

静态池决定：

- `该不该在池里`

动态池决定：

- `现在该不该先动`

这就是未来最合理的协作关系。

它现在已经具备：

- 稳定事实源
- 清楚画像体系
