# BusinessMaster 阶段盘点与下一阶段总体规划 M21-M26 v1

## 1. 阶段结论

BusinessMaster 当前主线仍然成立：

`知识库 -> 画像 -> 候选 -> enrich补证 -> promote上移 -> writeback治理 -> share消费`

项目已经越过“代码能否跑通”的阶段，进入“如何稳定扩容、如何提供可信潜客信息、如何保护知识资产来源边界”的阶段。

当前最重要的阶段性成果是：执行闭环已经完成真实写回验证，首批 `15` 家 L3 可消费池已经形成；M20 又把下一批 `30` 家候选从事实缺失型 block 解到画像边界型 warn。

当前最重要的阶段性瓶颈是：画像稳定性和业务确认仍是规模化写回前的核心闸门。继续扩大候选池之前，应优先把 `persona_boundary_unstable` 从系统性 warn 变成可人工确认、可规则沉淀、可反馈迭代的判断。

## 2. 系统设计回顾

### 2.1 整体目标

BusinessMaster 不是逐客户把档案修厚的文档工程，而是一套静态潜客经营系统。

系统应持续回答五个问题：

1. 哪些知识资产能定义我们关心的行业、场景和经营诉求？
2. 哪些公司符合这些画像，值得进入候选池？
3. 哪些候选已经具备足够事实和证据，可以上移到更高可消费层？
4. 上移后如何通过治理、证据和队列保持可解释、可追踪？
5. 业务使用者如何消费这些对象，并把反馈作为候选观察回流到规则校准，而不是直接覆盖知识库？

### 2.2 主链设计

当前主链应继续保持：

1. `知识库`：沉淀来自真实客户案例、解决方案、行业研究和权威材料的行业、案例、画像、证据等级和反例。
2. `画像`：把知识资产转成候选判断口径。
3. `候选`：按画像选择 L5 或边界对象进入执行批次。
4. `enrich补证`：补齐最小事实、产品服务、入池理由和强来源 evidence。
5. `promote上移`：通过本地规则判断 allow/warn/block。
6. `writeback治理`：只在 baseline、gate、integrity 全部通过后写回工作簿。
7. `share消费`：把复杂规则结果翻译成可信潜客摘要、风险和待补点；消费反馈只能作为观察线索。

### 2.3 设计合理性判断

当前设计是合理的，原因有三点：

1. 它把“判断依据”放在知识库和画像层，而不是散落在单个脚本或单个客户档案里。
2. 它把“写回”放在 gate 和 baseline 之后，避免 LLM 或批次脚本直接污染主表。
3. 它把“可消费”作为最终产出，而不是只追求表格字段更满或批次数量更大。

当前设计仍需补完的地方也很明确：画像边界需要业务确认机制，知识资产需要产品化入口，share 层需要真实反馈字段回流。

## 3. 已完成盘点

### 3.1 系统设计

已完成：

1. 已明确系统不是“逐客户档案修厚”，而是静态潜客经营系统。
2. 已固定主线：知识库驱动画像，画像驱动候选，上移驱动补证，档案负责承载，share 负责消费。
3. 已通过 M17/M18 证明系统可以产出真实可消费 L3 样本。

剩余问题：

1. 设计文档和执行产物之间仍有分散现象，需要继续收口到少数主入口。
2. 知识资产来源治理、画像规则校准、潜客观察回流尚未完全形成闭环。

### 3.2 执行层

已完成：

1. `select -> enrich -> promote -> report_only -> gate_check -> write_back -> post_integrity` 主链已可运行。
2. baseline、candidate signature、gate check、workbook integrity、serial lock 已成为稳定闸门。
3. M17 已完成真实写回：`promoted=15 / skipped=0`，工作簿完整性 `ok=true`。
4. M20 已完成 30 家批量补证 report-only/gate：`allow=0 / warn=30 / block=0`，未写回。

质量判断：

执行代码层已经进入“较成熟”阶段。后续重点不应是继续无限加脚本，而是把已验证脚本沉淀为标准运行手册、批次模板和交接包。

### 3.3 潜客池进展

当前进展：

1. 首批可消费 L3：`15` 家，M18 标记 `l3_share_ready=15`。
2. 下一批补证候选：`30` 家，M20 已完成最小字段与强来源补证，当前为 `warn=30`。
3. 更大候选池：M19 识别 L5 候选 `134` 家，其中 `needs_intake_patch=106`，`not_ready=28`。

质量判断：

静态潜客池已经进入“可消费早期”，但还不是规模化稳定供给。当前最有价值的不是马上把 134 家全部推进，而是把 15 家 L3 和 30 家 warn 样本用好，验证消费、反馈和画像确认机制。

### 3.4 质量与治理

已解决或显著收敛的问题：

1. `review_status` 历史状态兼容。
2. `missing_field` 批量补齐路径。
3. `official_source_missing` 官方来源补证路径。
4. `evidence_thin` 强 evidence 补证路径。
5. `generic_product` 与 `generic_admission` 泛化文本修复路径。

当前主瓶颈：

1. `persona_boundary_unstable` 仍是系统性 warn。
2. 画像转正尚缺明确人工确认或业务反馈信号。
3. 强 evidence 是必要条件，但不是自动 active 的充分条件。

### 3.5 LLM 增强层

当前状态：

1. LLM API 已配置，可通过项目委派脚本使用。
2. LLM 定位正确：做草稿、摘要、画像复核建议和知识抽象。
3. LLM 不得直接决定写回，不得绕过 evidence、规则和 gate check。

后续使用重点：

1. 辅助 M21 的画像确认说明草稿。
2. 辅助 M23 的业务反馈归纳。
3. 辅助 M24 的知识资产条目草拟。

## 5. 下一阶段里程碑规划（主线校正版）

基于用户对核心目标的校正，本阶段从“业务行动验证”重新收束为“可信画像匹配潜客池”建设。

核心目标：基于知识库和理想客户画像，持续找到匹配潜客，并为每个潜客提供核心、可靠、可解释的信息。

已生成的 M23A/M21 业务反馈类产物保留为可读性/使用性参考，但不再作为主线写回准入依据。

### 5.1 M21R：可信画像匹配复核，P0

输入：M20 的 `30` 家 `warn=30 / block=0` 样本。

目标：把 `persona_boundary_unstable=30` 从笼统 warn 转成可信度状态：

1. `trusted_match_ready`
2. `profile_match_pending`
3. `evidence_pending`
4. `persona_adjust_needed`
5. `not_icp`

成功口径：

1. 每家公司都有画像匹配结论。
2. 每家公司都有核心信息完整性判断。
3. 每家公司都有 evidence 可追溯性判断。
4. 每家公司都有风险/待补点。
5. 不因为缺少销售反馈而阻塞可信潜客判断。

### 5.2 M22R：可信潜客写回准入试点，P0/P1

前置：M21R 中出现 `trusted_match_ready` 对象。

目标：只把“画像匹配可信、核心信息可靠、证据可追溯”的对象纳入写回准入。

写回准入条件：

1. `trusted_match_ready`。
2. `official_evidence_coverage=true`。
3. `core_info_complete=true`。
4. `admission_reason_clear=true`。
5. `gate_check=PASS`。
6. `workbook_integrity ok=true`。
7. 用户单独确认真实 write_back。

成功口径：

1. 写回对象全部满足可信潜客定义。
2. `skipped=0`。
3. 写回后工作簿完整性 PASS。
4. share/摘要层能解释每家公司为什么匹配画像。

### 5.3 M23R：可信潜客摘要层，P1

输入：首批 15 家 L3 与 M21R 可信对象。

目标：生成可读、可复核的可信潜客摘要卡。

摘要卡字段：

1. 公司名称。
2. 匹配画像。
3. 匹配理由。
4. 核心产品/服务。
5. 经营结构或业务模式。
6. 关键 evidence。
7. 当前可信度状态。
8. 风险/待补点。

成功口径：

1. 读者能快速理解画像匹配理由和证据来源。
2. 风险/待补点清楚。
3. 不强制要求销售下一步动作。

### 5.4 M24R：知识资产来源治理与画像规则校准，P1

目标：明确知识库的来源边界，并把潜客批次暴露出的画像问题转成待验证观察，而不是直接沉淀成正式知识资产。

不可做：

1. 不把潜客公司当作真实客户案例。
2. 不把 M21R/M22R 的可信匹配结果当作画像正例或反例。
3. 不用潜客摘要覆盖 `knowledge_assets`、`persona_registry` 或正式案例材料。
4. 不让 LLM 从候选包归纳出“正式行业规则”并直接落库。

可做：

1. 生成 `candidate_observation`：哪些候选反复触发同类画像边界问题。
2. 生成 `source_gap`：哪些画像缺真实案例、解决方案或行业材料支撑。
3. 生成 `learning_queue` 补源任务：要求寻找真实客户案例、内部解决方案、行业研究或权威公开材料。
4. 生成 `rule_calibration_proposal`：只作为待评审规则建议，不自动生效。
5. 维护强 evidence 判定标准，但该标准只用于潜客信息可信度，不等同于客户案例资产。

### 5.5 M25R：可信扩容，P2

前置：M21R/M22R 完成；M24R 至少完成来源边界检查，确认不会把潜客观察误写为正式知识资产。

目标：从 30 家扩展到 50-100 家，但扩容依据是画像匹配和信息可信度，不是销售动作价值。

成功口径：

1. block 率可控。
2. `trusted_match_ready_count` 稳定增长。
3. 证据覆盖率和核心信息完整率不下降。
4. 扩容对象仍可解释、可追溯。

### 5.6 M26R：长期运行与交接固化，P2

目标：把脚本、配置、产物、复盘整理成长期运行机制。

成功口径：

另一个 agent 或另一台机器能无歧义恢复运行，并能理解当前核心指标是 `可信画像匹配潜客数`，不是销售行动数量。

## 6. 优先级判断

### 6.1 最高优先级：M21R

因为当前 M20 的 30 家已经从事实缺失型 block 解到 `warn=30 / block=0`，真正卡点是画像边界和可信信息状态，而不是业务是否马上跟进。

### 6.2 第二优先级：M23R

可信潜客池必须能被阅读和复核，所以摘要层仍重要。但它服务于“可靠核心信息表达”，不是销售动作管理。

### 6.3 第三优先级：M24R

M24R 的重点不是从潜客中总结知识资产，而是建立知识资产来源护栏。只有先确认“哪些材料可进知识库、哪些只能作为候选观察”，后续扩容才不会污染画像和知识库。

### 6.4 暂缓事项

暂缓：

1. 大规模 100+ 写回。
2. 追求 L2 高质量样本。
3. 大面积手工修档案。
4. 为所有 pending 做深补证。
5. 把系统改造成销售行动或商机管理流程。

## 7. 北极星指标

下一阶段采用北极星指标：`可信画像匹配潜客数`。

定义：同时满足以下条件的公司数量：

1. ICP/画像匹配明确。
2. 核心公司信息完整。
3. 关键 evidence 可追溯。
4. 入池/上移理由清楚。
5. 风险和待补点明确。
6. 当前治理状态可解释。

## 8. 下一步建议动作

推荐下一步执行 M21R：

1. 读取 M20 的 30 家 promote/report-only 结果。
2. 生成 M21R 可信画像匹配复核包。
3. 为每家公司计算可信度状态。
4. 生成可信潜客摘要卡模板。
5. 更新状态面板为 `trusted_match_ready` 指标。
6. 若出现 `trusted_match_ready`，再准备 M22R 写回准入材料。
7. 不执行真实 write_back，除非用户单独确认。

## 9. 验收标准

下一阶段不以“写回越多越好”或“业务是否马上跟进”为标准，而以以下标准验收：

1. 找得准：画像匹配结论清楚。
2. 说得清：匹配理由、核心信息和风险清楚。
3. 信得过：关键 evidence 可追溯。
4. 可治理：状态、queue、写回闸门清楚。
5. 可扩容：新批次不牺牲可信度。
6. 可隔离：潜客观察不污染正式知识资产。
7. 可迁移：另一个 agent 能按文档和脚本恢复运行。

## 9. Assumptions

1. 继续坚持当前主线设计，不改项目目标。
2. LLM 继续作为增强层，不直接决定写回。
3. 真实写回仍需单独确认。
4. M21 默认生成人工确认包和准入包，不默认改工作簿。
5. 下一阶段成功不以写回数量衡量，而以可解释、可消费、可追溯、可扩容且不污染知识资产衡量。
