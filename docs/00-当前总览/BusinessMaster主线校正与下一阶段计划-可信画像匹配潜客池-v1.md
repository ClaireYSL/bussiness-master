# BusinessMaster 主线校正与下一阶段计划：可信画像匹配潜客池 v1

## 1. 主线校正结论

BusinessMaster 的核心目标不是销售行动管理，也不是 CRM 线索推进，而是：

**基于知识库和理想客户画像，持续找到匹配潜客，并为每个潜客提供核心、可靠、可解释的信息。**

因此，后续所有 milestone、指标和产物都要围绕三件事展开：

1. 找得准：知识库和 ICP/画像能稳定筛出匹配公司。
2. 说得清：每家公司为什么匹配画像、适合哪个场景、还有什么不确定性。
3. 信得过：核心信息来自可信来源，并能追溯 evidence、规则和写回记录。

业务反馈、行动卡、下一步动作可以作为“可读性和使用性验证”，但不能反客为主，不能把项目变成销售流程或商机管理。

## 2. 对上一版路线的修正

上一版把 `M23A` 和 `M21` 往“业务是否愿意采取下一步动作”方向推进，这个视角有价值，但表达过重，容易把系统目标带偏。

本次修正如下：

1. `可行动静态潜客数` 改为 `可信画像匹配潜客数`。
2. `业务行动卡` 改为 `可信潜客摘要卡`。
3. `worth_following / recommended_next_action` 不作为主指标，只作为可选使用性反馈。
4. `confirm_active_high_value` 不作为核心写回口径，改为 `trusted_match_ready`。
5. M22 不再强调“业务高价值写回”，而强调“画像匹配可信、核心信息可靠、证据可追溯后写回”。

## 3. 新北极星指标

北极星指标：`可信画像匹配潜客数`

定义：同时满足以下条件的公司数量：

1. ICP/画像匹配明确。
2. 核心公司信息完整。
3. 关键 evidence 可追溯。
4. 入池/上移理由清楚。
5. 风险和待补点明确。
6. 当前治理状态可解释。

该指标不要求销售或业务立即行动，也不要求出现商机信号。它衡量的是静态潜客池作为可信信息资产的成熟度。

## 4. 产物口径修正

### 4.1 可信潜客摘要卡

每家公司输出一张简短摘要卡，字段包括：

1. 公司名称。
2. 匹配画像。
3. 匹配理由。
4. 核心产品/服务。
5. 经营结构或业务模式。
6. 关键 evidence。
7. 当前可信度状态。
8. 风险/待补点。

可选字段：业务使用反馈、下一步建议、人工备注。

### 4.2 可信度状态

建议统一状态：

1. `trusted_match_ready`：画像匹配明确、核心信息可靠、证据可追溯，可进入可信潜客池。
2. `profile_match_pending`：画像可能匹配，但边界仍需确认。
3. `evidence_pending`：画像可能匹配，但证据不足或核心字段未稳。
4. `persona_adjust_needed`：当前画像可能不准确，需要调整。
5. `not_icp`：不符合当前 ICP 或画像。

### 4.3 主指标

下一阶段主指标应改为：

1. `trusted_match_ready_count`
2. `profile_match_pending_count`
3. `evidence_pending_count`
4. `persona_adjust_needed_count`
5. `not_icp_count`
6. `official_evidence_coverage_rate`
7. `core_info_complete_rate`
8. `admission_reason_clear_rate`

业务反馈指标保留为辅助指标，不进入核心验收。

## 5. 下一阶段里程碑修订

### 5.1 M21R：可信画像匹配复核，P0

输入：M20 的 `30` 家 `warn=30 / block=0` 样本。

目标：把 `persona_boundary_unstable=30` 从笼统 warn 转成可信度状态：

1. `trusted_match_ready`
2. `profile_match_pending`
3. `evidence_pending`
4. `persona_adjust_needed`
5. `not_icp`

成功口径：

1. 每家公司都有画像匹配结论。
2. 每家公司都有核心信息完整性判断。
3. 每家公司都有 evidence 可追溯性判断。
4. 每家公司都有风险/待补点。
5. 不因为缺少销售反馈而阻塞可信潜客判断。

### 5.2 M22R：可信潜客写回准入试点，P0/P1

前置：M21R 出现 `trusted_match_ready` 对象。

目标：只把“画像匹配可信、核心信息可靠、证据可追溯”的对象纳入写回准入。

写回准入条件：

1. `trusted_match_ready`。
2. `official_evidence_coverage=true`。
3. `core_info_complete=true`。
4. `admission_reason_clear=true`。
5. `gate_check=PASS`。
6. `workbook_integrity ok=true`。
7. 用户单独确认真实 write_back。

成功口径：

1. 写回对象全部满足可信潜客定义。
2. `skipped=0`。
3. 写回后工作簿完整性 PASS。
4. share/摘要层能解释每家公司为什么匹配画像。

### 5.3 M23R：可信潜客摘要层，P1

输入：首批 15 家 L3 与 M21R 可信对象。

目标：生成可读、可复核的可信潜客摘要卡。

成功口径：

1. 每家公司摘要控制在核心字段内。
2. 读者能快速理解画像匹配理由和证据来源。
3. 风险/待补点清楚。
4. 不强制要求销售下一步动作。

### 5.4 M24R：知识资产来源治理与画像规则校准，P1

目标：保护知识库的来源可信度，并把潜客批次中暴露的问题转成“待验证观察”和“规则校准线索”，而不是直接沉淀成正式知识资产。

核心边界：

1. 潜客不是已服务客户，也不是真实案例，不能作为 `customer_case`、画像正例或解决方案样板写入正式知识资产。
2. M21R/M22R 的候选结果只能证明“这些公司与当前 ICP/画像匹配且核心信息可追溯”，不能反向证明画像定义正确。
3. 潜客批次可以产出 `candidate_observation`、`hypothesis_to_validate`、`source_gap`、`persona_boundary_question`。
4. 只有当观察被真实客户案例、已验证解决方案、行业研究或权威公开材料支撑后，才允许进入 `knowledge_assets`。

第一版产物：

1. 知识资产来源白名单与禁用来源清单。
2. 潜客观察包：记录哪些画像边界需要回到真实素材验证。
3. 画像规则校准清单：只提出待验证调整，不直接改画像定义。
4. 强 evidence 判定标准：可来自官方/年报/IR/CNINFO，但只用于潜客可信信息，不等同于客户案例。
5. learning_queue 补源任务：要求补真实案例、解决方案或行业材料，而不是把潜客总结当素材。

### 5.5 M25R：可信扩容，P2

前置：M21R/M22R 完成；M24R 至少完成来源边界检查，确认不会把潜客观察误写为正式知识资产。

目标：从 30 家扩展到 50-100 家，但扩容依据是画像匹配和信息可信度，不是销售动作价值。

成功口径：

1. block 率可控。
2. `trusted_match_ready_count` 稳定增长。
3. 证据覆盖率和核心信息完整率不下降。
4. 扩容对象仍可解释、可追溯。

## 6. 当前已生成 M23A/M21 产物的处理方式

已生成的 M23A/M21 产物不删除，也不回滚，但重新定位为：

1. M23A：作为“可读性/使用性反馈包”，不是核心业务行动指标。
2. M21：作为“画像+业务价值确认包”的历史尝试，后续由 M21R 可信画像匹配复核取代。
3. 其中的 `worth_following / recommended_next_action` 只作为辅助字段，不进入主写回准入。

## 7. 下一步执行建议

下一步应从外部专家建议中的“行动卡 lite”改为“可信潜客摘要卡 lite”：

1. 生成 M21R 可信画像匹配复核包。
2. 为 M20 的 30 家计算可信度状态。
3. 生成可信潜客摘要卡模板。
4. 更新状态面板为 `trusted_match_ready` 指标。
5. 若出现 `trusted_match_ready`，再准备 M22R 写回准入材料。
6. 真实 write_back 仍需单独确认。

## 8. 不做事项

当前明确不做：

1. 不把系统改成销售线索跟进系统。
2. 不把 `worth_following` 当作潜客池核心指标。
3. 不因为没有业务反馈就否定画像匹配潜客。
4. 不直接进入 M22/M25 大规模写回或扩容。
5. 不让 LLM 输出绕过 evidence 和本地规则。

## 9. 校正后的判断

项目接下来要证明的不是“业务是否马上愿意跟”，而是：

**我们能否基于知识库和 ICP，稳定找到匹配公司，并为它们提供可靠、可解释、可追溯的核心信息。**
