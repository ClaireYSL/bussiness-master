# 静态潜客池-主线恢复版总说明 v1

## 1. 这份文档解决什么问题

这份文档用于把当前工作区重新拉回主线。

前一阶段执行里，`客户档案逐客户修复` 被持续放大，容易让后续工作误以为当前系统的核心任务是：

- 把每一家客户档案修得更厚
- 把页面前半部分补得更满
- 把 `L3+` 档案页做成主要工作对象

这不是当前静态潜客池的主目标。

当前系统真正要解决的问题仍然是：

1. 持续学习真实素材，形成可复用知识库
2. 基于知识库形成更稳定的主线与画像
3. 基于画像去发现更匹配的潜客候选
4. 在候选上移过程中逐步补强信息、重判可信度与匹配度
5. 最终形成一套可持续扩池、可解释、可校验的静态潜客经营底座

一句话恢复主线：

- `知识库驱动画像，画像驱动找潜客，上移驱动补信息，档案只负责承载和投影`

## 2. 当前系统的正确闭环

当前应固定为下面这条顺序，而不是倒过来。

### Step 1：原始素材持续学习

输入来源是：

- 真实客户案例
- 方案材料
- 官方公开材料
- 已验证项目经验
- 研究资料
- 上移过程中暴露出的素材缺口所反向补回的真实材料

这一层的目标不是生成结论，而是：

- 扩充原始素材池
- 抽取正式知识资产
- 维持学习队列

### Step 2：知识库增强主线与画像

知识库不是摆设，它要用于稳定回答两类问题：

1. 我们到底在找哪几类公司
2. 为什么这些公司更像目标客群

因此知识资产要继续沉淀到：

- `track_registry`
- `persona_registry`
- 管理诉求画像
- 话术和方案映射

这一层的目标是让“找什么样的公司”越来越稳定，而不是每次从零主观判断。

- [persona_registry_v1-字段模板-v1.md](/Users/clairaipartner/.openclaw/workspace-main/bussiness-master/docs/02-注册表与结构/persona_registry_v1-字段模板-v1.md)

### Step 3：基于画像扩展 L5 候选

新增潜客的默认逻辑不是“先看到公司，再想办法解释”，而是：

1. 先有较稳定的主线与画像
2. 再沿画像去找相邻公司
3. 用最小证据和边界规则判断是否能进入 `L5`

`L5` 的核心角色是：

- 候选层
- 待继续判断层
- 静态池的最小合法入口

不是：

- 成熟潜客层
- 已经足够扎实的档案层
- 动态优先级层

### Step 4：在上移过程中补强信息与重判

从 `L5 -> L4 -> L3 -> L2 -> L1` 的过程中，真正要发生的是：

1. 补主体与证据
2. 补公司级静态事实
3. 重判 `信息扎实度`
4. 重判 `ICP匹配概率`
5. 重判 `静态潜客记录成熟度`
6. 决定是否正式上移

也就是说：

- 信息补强应服务于上移判断
- 档案完善应服务于事实可读与共享消费
- 不是先把所有档案都修满，再决定谁值得判断

## 3. 四层职责重新钉死

为了避免后续再次偏航，当前四层职责重新明确如下。

### 3.1 知识层

回答：

- 我们已学到了哪些可复用认知
- 这些认知支撑哪些主线、画像和判断

载体：

- `knowledge_asset_registry`
- `raw_material_inventory`
- `learning_queue`

### 3.2 判断层

回答：

- 这家公司属于哪条主线
- 更像哪个业务形态画像
- 可能对应哪些经营诉求
- 当前匹配概率和记录成熟度如何

载体：

- `track_registry`
- `persona_registry`
- 主表中的判断字段

### 3.3 候选与上移层

回答：

- 哪些公司可以进入 `L5`
- 哪些候选接近上移
- 本轮上移补什么信息
- 补完后是否升层

载体：

- `external_target_account_pool_v2`
- `account_evidence_log`
- `account_review_queue`

### 3.4 档案与阅读层

回答：

- 这家公司当前已知信息如何被人快速读懂
- 团队共享、专题包和浏览层如何消费这些内容

载体：

- `潜客档案库`
- `L3+` 客户档案页
- 重点公司 note
- 专题包

这一层很重要，但它不是主驱动层。

## 4. 客户档案修复应放回什么位置

`客户档案逐客户修复` 的正确位置是：

- `Milestone 3` 的支持性工作
- 阅读层与共享层质量增强动作
- 上移与团队消费的辅助基础设施

它不应被理解为：

- 当前仓库第一优先级总任务
- 静态潜客池的核心业务闭环
- 知识库建设的替代物
- 画像扩展和候选发现的前置条件

更具体地说：

### 它能解决的事

- 让 `L3+` 页面更可读
- 让共享材料更稳定
- 让上移时少重复查资料
- 让团队浏览和解释更顺手

### 它不能替代的事

- 不能替代知识库持续学习
- 不能替代画像建模
- 不能替代 `L5` 候选扩展
- 不能替代上移判断本身

所以正确关系应是：

- `档案修复服务主线`
- 不是 `主线服务档案修复`

## 5. 当前默认优先级应该怎么排

如果没有用户额外改方向，当前默认优先级建议恢复为：

1. 继续吃真实素材，维护知识库和学习队列
2. 补强或校准主线与画像定义
3. 按主线/画像继续扩 `L5`
4. 只在明确范围下做一小轮上移
5. 在上移对象上定向补信息
6. 按需修复会阻碍上移或共享消费的档案

不建议再默认进入的状态是：

- “先把所有客户档案继续逐个修完”
- “先把页面做厚再谈候选和上移”
- “把档案是否完整当成当前系统的核心产出”

## 6. 当前阶段的默认工作判断

后续只要碰到任务分歧，可以先用下面几条判断。

### 判断 1：这项工作有没有直接增强知识库或画像体系

如果有，优先级通常更高。

### 判断 2：这项工作有没有直接带来新的 `L5` 候选或更好的候选发现能力

如果有，优先级通常高于纯页面修饰。

### 判断 3：这项工作有没有直接帮助一轮上移完成闭环

如果有，可以做，但应围绕“小批量上移对象”定向补，而不是大面积修页面。

### 判断 4：这项工作只是让已有档案更完整、更好看，但不改变候选发现或上移判断

这类工作属于支持层，不应默认吞掉整个 session。

---

## 7. 恢复后的执行口径

从这份文档开始，后续默认口径恢复为：

1. `先知识，后画像`
2. `先画像，后扩池`
3. `先候选，后上移`
4. `在上移中补证和补事实`
5. `档案层按需修，不再反客为主`

如需继续做客户档案修复，应附带明确目的，例如：

- 为某一轮 `L4 -> L3` 候选补强
- 为某个专题包或共享材料补阅读层
- 为一批重点公司补可解释页面

如果没有这些明确目标，默认不把“逐客户修档案”作为主任务。
