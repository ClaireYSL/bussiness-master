# 静态潜客池-污染止血与可信底座重建方案 v1

## 1. 当前判断

当前项目已不适合继续沿着“修客户档案内容”推进。

原因不是个别页面质量差，而是：

1. 全量客户档案内容已经普遍失真
2. 档案层失真意味着潜客事实层、解释层、入池理由、上移依据都可能已被污染
3. 如果继续基于现有档案做扩池、上移、解释和共享，只会继续放大错误

因此当前阶段的核心目标应立即切换为：

- `停止污染扩散`
- `重建可信最小事实底座`
- `用小样本校准整条生产线`

而不是：

- 继续逐客户修厚页面
- 继续消费现有档案内容
- 继续把不可信内容回写为新的判断依据

---

## 2. 当前问题的本质

这次问题本质上不是“页面不够好”，而是“数据生产线失真”。

失真通常发生在以下几个环节：

1. 用模板句、泛化句、画像句回填公司事实
2. 用解释层内容反向冒充事实层
3. 用阅读层产物反向充当知识源
4. 用页面厚度替代信息可信度
5. 用已有候选样本反向锁死知识库和画像

一旦发生这些问题，就会形成一条错误闭环：

- 失真的档案
- 失真的解释
- 失真的入池理由
- 失真的上移判断
- 再生成更多失真的档案

所以现在不能继续在结果层修补，而要回到源头拆掉这条错误闭环。

---

## 3. 第一阶段：立即止血

### 3.1 立即暂停的动作

从现在开始，默认暂停以下动作：

1. 基于现有客户档案内容继续扩 `L5`
2. 基于现有客户档案内容继续做批量上移
3. 基于现有客户档案内容继续做大面积逐客户修复
4. 基于现有客户档案内容继续生成共享解释材料
5. 基于现有客户档案内容继续补知识资产或画像映射

暂停原因很简单：

- 当前档案内容本身已经不能被视为可信输入

### 3.2 立即降级为“不可信消费层”的内容

以下内容先默认视为不可信消费层，不能直接驱动判断：

1. `L3+` 客户档案页正文
2. 主表中的解释性长文本
3. 依赖档案页生成的入池理由
4. 依赖档案页生成的上移说明
5. 依赖档案页反推的知识映射与话术映射

说明：

- 这不代表它们必须删除
- 只代表它们暂时不能当作判断依据继续使用

### 3.3 当前仍可保留的骨架

当前项目中，相对可保留的基础骨架是：

1. canonical account 与 alias 治理
2. 老客排除机制
3. evidence log 的表结构与字段框架
4. review queue 的表结构与流程框架
5. knowledge asset registry 的表结构
6. learning queue 的入口机制
7. track / persona registry 的结构框架

也就是说：

- 现在要保的是结构和机制
- 不是现在这批已经失真的内容本身

---

## 4. 第二阶段：重建可信最小底座

### 4.1 重建目标

这一阶段不是恢复“完整档案”，而是恢复“可信判断能力”。

目标是建立一个低配但可信的最小事实源，使系统至少能稳定回答：

1. 这家公司是谁
2. 它大致做什么
3. 它为什么可能属于某条主线或画像
4. 我们当前到底知道多少、还缺什么

### 4.2 可信最小字段集

在这一步，只允许先恢复以下字段：

1. `account_id / canonical_name`
2. `official_source_ready`
3. `high_confidence_source_ready`
4. `公司产品与服务概述`
5. `商业模式概述`
6. `primary_track`
7. `persona_tag`
8. `admission_reason_summary`
9. `validation_gap`
10. `evidence_refs`

控制原则：

- 只恢复最能支撑判断的字段
- 不追求页面完整
- 不追求字段铺满
- 不允许为了完整感填泛化句

### 4.3 可信来源顺序

只允许按以下顺序取材：

1. 官网
2. 年报 / 财报 / 招股书 / IR
3. 官方新闻 / 官方招聘页
4. 交易所公告
5. 权威公开资料

明确禁止：

1. 用旧档案页当事实源
2. 用重点公司 note 当事实源
3. 用专题包摘要当事实源
4. 用模型总结当事实源
5. 用画像模板句倒推公司事实

### 4.4 当前重建输出应是什么

这一阶段的输出不应是“新的一版漂亮档案”，而应是：

1. 一批可信最小记录
2. 每条记录对应的真实来源
3. 清楚的待验证项
4. 对主线 / 画像的阶段性判断

一句话说：

- 先恢复“能判断”
- 再考虑“好不好看”

---

## 5. 第三阶段：小样本校准

### 5.1 为什么不能直接全量返工

如果不先校准，就直接全量翻修，风险很高：

1. 可能按错误画像继续重建一遍
2. 可能把本应出池的对象继续修进池里
3. 可能继续用错误上移口径放大偏差

所以必须先抽样，不得直接全量开工。

### 5.2 建议校准样本集

建议先抽一个小样本集：

1. 每条主线各 `10-20` 家
2. 覆盖 `L5 / L4 / L3 / L2`
3. 同时包含：
   - 看起来最稳的对象
   - 边界模糊对象
   - 之前被上移过的对象
   - 之前档案看起来很厚但可疑的对象

### 5.3 校准时要回答的三个问题

1. 现有画像还能不能稳定解释这批对象
2. 现有 `L5` 中有多少其实不该入池
3. 现有 `L3/L2` 中有多少只是页面变厚，但并没有更可信

### 5.4 校准后的决策门槛

如果样本校准后发现：

- 误判率低
- 画像仍稳定
- 主要问题只是事实字段薄

则可以继续做局部重建。

如果发现：

- 入池理由普遍失真
- 画像归属大量不稳定
- 上移结果与真实来源明显不匹配

则不应修旧内容，而应直接进入分层重建。

---

## 6. 第四阶段：分层重建，而不是全量补丁

如果校准结果显示污染较深，建议按层重建。

### 6.1 L5 层

处理方式：

- 重新做入池校验
- 不满足可信最小标准的，降为待观察或移出

### 6.2 L4 / L3 层

处理方式：

- 重新做上移前核验
- 不满足的退回待验证状态
- 不再保留“因为页面厚所以已上移”的结果

### 6.3 L2 / L1 层

处理方式：

- 只保留能被真实证据重新支撑的对象
- 不能支撑的，降级或转回复核队列

这一步的目标是：

- 重建层级可信度
- 不是维护历史体面

---

## 7. 当前项目的建议执行顺序

建议把项目切成以下顺序：

1. 先冻结基于旧档案的消费链路
2. 明确哪些表结构保留、哪些内容降级为不可信
3. 定义可信最小字段集
4. 抽样重建一批校准样本
5. 用样本结果校准主线、画像、入池与上移口径
6. 再决定分层重建范围

当前不建议的顺序是：

1. 继续修现有档案
2. 一边修一边继续扩池
3. 一边修一边继续上移
4. 修完后再判断是否可信

这是错误顺序。

---

## 8. 现在最值得立刻做的三件事

### 8.1 先写“冻结口径”

明确从今天起：

- 旧档案不得继续直接驱动扩池和上移

### 8.2 先定义“可信最小字段集”

没有这个字段集，后面所有重建都会重新发散。

### 8.3 先做一批校准样本

没有样本校准，就没有资格决定是否全量返工。

---

## 9. 这一版方案的核心结论

当前项目不该继续以“修内容”为目标，而应切换为：

- `重建可信数据生产线`

这条新主线应固定为：

1. `止血`
2. `重建可信最小底座`
3. `小样本校准`
4. `分层重建`

如果不先这样切换，后续所有“修复”都很可能只是在继续生产看起来更完整、但实际上更不可信的内容。
